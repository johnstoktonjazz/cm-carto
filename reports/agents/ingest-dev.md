## Принятые решения по ходу (без правки DECISIONS.md)

1. Проверка охвата: все объекты должны попасть в `extent_wgs84` проекта, иначе ingest падает. Так ловятся перепутанные оси, чертеж в местной системе или миллиметрах. Единицы и `$INSUNITS` DXF отдельно не проверяются.
2. Разрыв меньше 1 см (шум округления дуг) в отчете одной строкой на слой, больше — отдельной строкой с местом.
3. Один номер в нескольких контурах — один объект (объединение), несколько номеров в одном контуре или нет номера — ключ по геометрии и строка «требует подтверждения».
4. Статус берется из правил (`official` у ППТ, `cadastral` у КПТ, `reference` у чужих файлов); паспорт источника статус не меняет.
5. ОКС из КПТ (`build_record`), ПЗЗ-чертежи и генплан в DXF не разбираются: нужны отдельные правила (`rules/pzz.yaml`, `rules/genplan.yaml`) на реальных образцах.

## Ограничения

- Типы HATCH, SOLID, 3DFACE, POINT на слоях с правилами попадают в «не распознано» (`правило не разбирает`).

### Использование (для проекта)

В `project.yaml`: `rules: rules` (папка от папки анкеты). В ней `ppt.yaml` (или `egrn.yaml`, `vector.yaml`) с `extends: ppt` и только своими `layers`; паспорт чертежа ссылается на то же имя (`rules: ppt`). Раскладка, которой в модуле нет (например, чертеж ГПЗУ), — самостоятельный файл `<имя>.yaml` с полным набором ключей и паспорт `rules: <имя>`.

### Абзац для README корня (на правку оркестратору)

> **Правила раскладки проекта.** Типовые правила (`rules/`) не знают имен слоев чертежей конкретного проекта. Поле `rules: <папка>` в `project.yaml` (от папки анкеты) указывает папку правил проекта: файл `<имя>.yaml` в ней берется вместо модульного. Файл с `extends: <имя правил модуля>` дополняет модульные правила: его `layers` (для выписки — `zouit_types`, `pzz.zones`) проверяются раньше модульных, `ignore` добавляется, остальные ключи заменяют. Файл без `extends` — самостоятельная раскладка (например, чертеж ГПЗУ). Итог проверяется схемой и контрактом; в шапке отчета импорта названы примененные файлы, оба входят в `input_hash` части.

### Ограничения

- Кеш правил живет в процессе: правка файла правил во время работы процесса подхватывается после перезапуска (для команды `ingest` это один запуск).
- Проверка опечаток в файле проекта идет по итогу слияния; номер записи в сообщении схемы (`layers/0`) считается в итоговом списке, где записи проекта идут первыми.
